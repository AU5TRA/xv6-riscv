Reference configuration
-----------------------

CPUS=1 is the correctness claim. CPUS=3 is stress only: no cross-hart TLB
shootdown is implemented, so multicore paging correctness is NOT claimed.

  QEMU memory      128 MiB      (never reduce it to create pressure; the
                                 resident-frame limit inside xv6 is the
                                 knob, and PHYSTOP is assumed reachable)
  Host             WSL2 Ubuntu 24.04.4 LTS on Windows 11
  Kernel           Linux 6.18.33.2-microsoft-standard-WSL2 x86_64
  Compiler         riscv64-unknown-elf-gcc 13.2.0 (13.2.0-11ubuntu1+12)
  Linker           GNU ld 2.42 (2.42-1ubuntu1+6)
  QEMU             8.2.2 (Debian 1:8.2.2+ds-0ubuntu1.18)
  Python           3.12.3
  pexpect          4.9.0

The compiler, QEMU and Python packages are unpacked under
/home/ashfaq/.local/xv6-tools and put on PATH by /home/ashfaq/xv6env.sh,
because this machine does not grant passwordless sudo. They are not part
of the repository or the experiment output.

fs.img lives on a 9p-mounted Windows drive under WSL2. That detail affects
the timings below and nothing else.

The checkout is owned by Windows Git with core.autocrlf=true. `git status`
and `git diff --check` are run through Windows Git so unchanged CRLF files

`-c core.autocrlf=true` for the same reason. .gitattributes pins *.sh and
*.py to LF so a script checked out on Windows still runs under WSL.

Recorded baselines
------------------

Source: `vmtest baseline` and `vmtest data-invariance`. Both run one
deterministic 64-page workload -- write the pattern, read it back four
times alternating direction, then 1024 pseudorandom probes -- in a forked
child so every configuration starts from an identical state, under a
resident limit of 35 frames against a start_resident of 27.

Determinism, measured rather than assumed:

  * Every SYNCHRONOUS row below is bit-identical between the release and
    the VM_DEBUG build and across repeated runs of the same tree. The
    prefetch-disabled table is likewise identical in both builds.
  * ASYNCHRONOUS rows reproduce in DATA only. The worker is scheduled
    concurrently with the workload, so eviction and prefetch counts move
    by up to about 2% between runs (Clock async: 1714 debug, 1721
    release). Dataset collection that needs counter-level reproducibility
    must use synchronous prefetch or none.
  * The counts are a property of THIS BUILD of the test program, not of
    the policy alone. Changing user/vmtest.c changes the binary's page
    layout, which changes which of the process's own pages are cold, which
    moves the counts: Clock read 1327 baseline faults before the
    random_workload fix and 1325 after, with no change to either the
    policy or the measured workload. Re-record this table whenever the
    workload binary changes, even if its logic did not.

1. Policy baseline, prefetch disabled (limit=35, start_resident=27, 64 pages)

  policy   swap_faults  evictions  page_reads  page_writes  fallbacks
  FIFO           1440       1496        1440           95          0
  Clock          1325       1381        1325           94          0
  Aging          1405       1461        1405           95          0

  Clock is 8.0% better than FIFO on this workload and Aging sits between
  them. The spread is small, which is itself worth remembering when
  Phase 5 measures the Clock-to-Belady gap.

2. Policy x prefetch matrix (limit=35, prefetch enabled and automatic)

  policy  mode   checksum   evict  faults  reads  writes  pf_acc  pf_use  pf_waste
  FIFO    sync   AB0C8578    1567    1039   1511      95     472     414        48
  FIFO    async  AB0C8578    1567    1039   1509      95     472     414        48
  Clock   sync   AB0C8578    1746    1127   1690      94     563     215       347
  Clock   async  AB0C8578    1721    1102   1664      94     563     235       325
  Aging   sync   AB0C8578    1489    1000   1433      95     433     413        14
  Aging   async  AB0C8578    1487     998   1429      95     433     415        12

  Async rows are the release build; the debug build gave 1567 / 1714 /
  1487 evictions for the same three.

  All six checksums equal AB0C8578, which is also the value computed from
  the pattern definition alone without touching memory. Identical data,
  materially different mechanics: 17% spread in evictions, 13% in swap
  faults, and a factor of 29 in wasted prefetches.

3. Randomised soak (`vmtest random <seed> 100000`, 51 pages, limit 35)

  seed 1: 37,495 swap faults, 37,538 evictions, 19,744 page writes.
  Ten seeds pass in each configuration: 1 2 3 4 5 17 31 127 1024 65535.

Measured trace-capture envelope
-------------------------------

A capture is lossless only while the drainer keeps up with the emitter. On
one CPU the two share the processor, so the meaningful measurement is the
fraction of the stream that survives, not either rate in isolation.

  vmtest swap-repeat   28,274 records, 0 drops          -- lossless
  vmtest random 1e5   302,243 emitted, 142,629 dropped  -- REJECTED

Composition of the rejected capture, from tools/decode_trace.py:

  emitted                        302,243   (deterministic across runs)
  reached the file               161,285   53.4%
    of which DROP markers         65,588
  arrived with an intact type     95,697   31.7%
  never arrived at all           140,958   46.6%

Rates during that run (workload 152.4 s, excluding boot and build):

  emission                 ~1,980 records/s
  drain                    ~1,050 records/s  (~66 KB/s of 64-byte records)
  cost of tracing          72.5 s -> 152.4 s, i.e. 2.1x wall clock

The emitted count is deterministic (302,243 in all three runs). The dropped
count is not (142,629, 140,958), because it depends on how the drainer and
the workload interleave.

The ring buys a fixed backlog rather than a rate: the capture above stayed
perfectly lossless for its first 30,725 records, then lost roughly 550
events before every subsequent 256-record drain batch.

Both outcomes are in the matrix on purpose. The second is the evidence
that the drop discipline fires; a capture that overruns is discarded
whole, never truncated to the part that survived.


Test-plan deviations carried forward
------------------------------------

Upstream xv6 `grind` runs forever by design. Its default behaviour is
kept; an optional per-worker operation count was added for automation, so
`grind 200` terminates with a PASS marker.

Synchronous versus asynchronous prefetch is selected with VM_PREFETCH_MODE.
Automatic next-page prediction has its own VM_PREFETCH_AUTOMATIC switch so
explicit duplicate and race experiments stay deterministic.

VM_PREFETCH_MODE is refused while anything is queued or in flight, so a
test that switches modes has to drain first (vmtest quiesce_prefetch()).
vmcheck() has the same precondition: an async prefetch in flight owns a
frame in VM_PAGE_RESIDENT_PREFETCH whose PTE is not installed yet, and
vmcheck correctly reports that as a pte mismatch.
