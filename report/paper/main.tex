% Abstract: 150-220 words (median 180). Sentence roles, in order: context; problem

% CLAIM STATUS: PENDING decision D2 (AUSTRA_HANDOFF.md, START HERE section 1). The
% claim below is the one the handoff proposes; confirm it with the collaborator before

Learned policies beat hand-written heuristics in CPU caches and content-delivery
networks, but an operating system's page-replacement policy works under constraints
those settings lack: the kernel never sees individual memory accesses, cannot use
floating point on the eviction path, and every eviction changes all later faults.
We ask whether a learned page-replacement policy is implementable under these
constraints, and build one in the xv6 teaching kernel. It scores resident pages with a
small linear model over signals the kernel already keeps (accessed- and dirty-bit
history and refault bookkeeping), computed in whole-number arithmetic and trained
offline to imitate \belady's optimal policy.
Across 14 workloads, eight of them never used in training, and 2,375 kernel runs at
three memory sizes, the linear score incurs 8.6\% fewer page faults than \clock at 10\%
memory (95\% interval 2--15\%) and is level with ARC, the strongest classical policy we
could run in the kernel. Five heavier models, including a CNN and an MLP, are not
clearly better and cost 20--150$\times$ as much per eviction.
Decision time is the price: 22,803 instructions per eviction, 55$\times$ \clock;
sampling 32 candidates halves it for at most one point of faults.

% --- Move 2: how the OS does it today, and the measured failure --------------
Operating systems choose which page to evict with recency heuristics built on the
hardware accessed bit: \clock and its descendants~\citep{corbato1968paging,carr1981wsclock},
and in Linux the active/inactive lists and the multi-generational LRU~\citep{linux_mglru}.
These heuristics leave a large gap to the optimum. On B-tree, key-value and graph
workloads, \belady's offline policy~\citep{belady1966study} incurs 43--54\% fewer faults
than \clock, and \clock is within 2\% of exact LRU on five of the six training
workloads (\S\ref{sec:bg-headroom}). Stronger classical policies such as
ARC~\citep{megiddo2003arc}, LHD~\citep{beckmann2018lhd} and
S3-FIFO~\citep{yang2023s3fifo} were designed for caches that see every hit; in the form
a kernel can run, the best of them, ARC, incurs about 5\% fewer faults than \clock
(Table~\ref{tab:teaser}).

% --- Move 3: why prior learned approaches do not solve it --------------------
% DRAFT written with an AI assistant from related-work-notes.md. MLSys forbids text
% generated by an LLM alone: rewrite it in your own words before submission, and check
% each claim against the cited paper. Do not add a "first" claim (LearnedCache exists).
Learned replacement policies already beat hand-written ones, but in settings that see
every access. Hardware cache policies learn from \belady's decisions using per-access
program counters~\citep{jain2016hawkeye,shi2019glider,shah2022mockingjay}, or imitate
\belady with a neural policy~\citep{liu2020parrot}. Content-delivery and storage caches
learn from the history of every request, in floating point, outside the
kernel~\citep{song2020lrb,song2023halp,vietri2018lecar,rodriguez2021cacheus}. A kernel
has none of this: it learns about a page only when the page faults or when a scan finds
its accessed or dirty bit set, and it must pick a victim on the eviction path without
floating point. The closest work, LearnedCache~\citep{qi2026learnedcache}, runs a
perceptron inside the Linux page cache through cache\_ext~\citep{zussman2025cacheext},
but it sees every page-cache access and manages file pages, not a program's memory.
Learned operating-system policies at MLSys have so far worked above the kernel, in VM
allocation~\citep{barbalho2023vmalloc,ling2025lava}, NUMA placement~\citep{zhao2026catur}
and storage placement~\citep{yang2025byom}. Whether a learned policy can work with only
what a kernel sees has remained open.

% --- Move 4: the question and the insight ------------------------------------
This paper asks whether a learned page-replacement policy is \emph{implementable} at
operating-system level: with only the signals a kernel observes, without floating point,
on the eviction path, and without knowing which program it serves. Our answer is a
qualified yes: \textbf{the kernel already sees enough}. Accessed-bit history and the
refault bookkeeping kernels already keep carry the signal a learned policy needs; a
small linear score over them, computed in whole numbers, beats \clock inside the kernel
and is level with the strongest classical policy a kernel can run. Larger models do not
pay for their cost.

Our contributions are:

\subsection{Page Replacement, as the Kernel Sees It}
\label{sec:bg-mechanism}

\plan{For ML readers, in about 0.5 page. (1) A process has more virtual pages than its
resident limit allows; touching a non-resident page traps (a page fault); the kernel
must pick a resident \emph{victim}, write it back if it is dirty or has no swap copy,
and load the faulting page. (2) The decision: which resident page to evict; made once
per eviction, synchronously on the fault path; its budget is set by the fault it
serves (a disk read, often a write). (3) What the kernel can see: the MMU handles loads
and stores itself and only sets the accessed (A) and dirty (D) bits in the page-table
entry; the kernel reads and clears them when it scans. It never sees individual
accesses. Linux has the same limit for anonymous memory. (4) \clock and Aging as
heuristics over the A bit; \belady as the offline optimum (evict the page whose next
use is furthest away), optimal for faults but not for writes.}

\subsection{Heuristics Leave Large Headroom}
\label{sec:bg-headroom}

\obs{1}{\clock is as good as exact LRU, and both are far from optimal.}
On the six workloads used for training (\S\ref{sec:eval-setup}), \clock is within 2\%
of exact LRU on five, xv6's Aging is barely better than FIFO, and the only classical
policy that beats \clock anywhere, exact LFU, is catastrophic elsewhere
($\geq3\times$ \clock on graph, sort and matmul). \belady needs 43--54\% fewer faults
than \clock on the B-tree, key-value and graph workloads, 53--59\% on LZW, 38\% on
matmul, and only 10--17\% on sort (Figure~\ref{fig:headroom}).
$\rightarrow$ \emph{Recency and frequency both carry signal, but every fixed combination
fails on some workload; a policy should learn the combination.}

\subsection{The Kernel's Coarse Signals Carry the Information}
\label{sec:bg-signals}

\obs{2}{What the kernel can sample nearly matches what an oracle trace records.}
We rank each feature against the true next-use distance \emph{within} each eviction
decision, because choosing among the candidates of one decision is all a policy does.
Measured that way, the kernel's sampled access count \feat{sfreq} is about as
informative as the exact count \feat{freq} that only a full trace gives (mean over the
six training workloads $-0.27$ vs.\ $-0.24$; btree $-0.53$ vs.\ $-0.59$, kv $-0.47$ vs.\
$-0.54$), and the refault distance that Linux's workingset code already measures is the
strongest of the three ($+0.32$) (Figure~\ref{fig:diagnostics}).
$\rightarrow$ \emph{Use kernel-observable features, and train and judge them on eviction
decisions, not on individual references} (\S\ref{sec:design-features},
\S\ref{sec:design-train}).

\subsection{A Naively Trained Policy Fails}
\label{sec:bg-naive}

\obs{3}{Trained on uniformly sampled candidates, a learned policy evicts the page the
program is streaming through.}
With \belady's choice plus 31 uniformly sampled candidates per recorded eviction, almost
every linear model was $\geq3\times$ \clock on PageRank, even one trained on PageRank
alone, and three rounds of DAgger~\citep{ross2011dagger} did not help. 97\% of its
victims had been loaded at the immediately preceding fault and were needed again a
median of 16 references later; \belady's choice at the same decisions had last been used
about 300 references earlier. Out of 167 resident pages, the one or two just touched are
almost never sampled, so the model never learned to keep them.
$\rightarrow$ \emph{The training distribution must contain just-used pages, and new pages
need protection} (\S\ref{sec:design-train}).

\subsection{Research Questions}
\label{sec:bg-rq}

Whether a learned policy is implementable in a kernel breaks into four questions,
answered in \S\ref{sec:eval}:
\begin{description}
\item[RQ1 Information.] Do kernel-observable signals suffice, or does a learned policy

\item[RQ2 Effect in the kernel.] Inside a real kernel, does the policy beat \clock and

\end{description}

\subsection{Overview and Formulation}
\label{sec:design-overview}

\plan{Walk Figure~\ref{fig:overview} in decision order.
\emph{Offline}: complete reference strings $\rightarrow$ replay under LRU at 5/10/20\%
memory $\rightarrow$ record eviction decisions (candidates, features, label)
$\rightarrow$ fit a linear scorer $\rightarrow$ select feature subset and probation on
validation only $\rightarrow$ export integer weights.
\emph{Online}: at each eviction the kernel scans the eligible resident pages, updates
their counters, scores each with an integer dot product, protects pages in probation,
and evicts the highest score (oldest load on a tie).}

\plan{Formulation, and why this kind of ML. The policy imitates \belady: for each
candidate it regresses $\log(1+d)$, where $d$ is the distance in references to the
page's next use (capped at $2^{20}$), and evicts the candidate with the largest
prediction. Supervised imitation fits because complete reference strings give exact
labels offline and \belady is optimal for faults; reinforcement learning would need
exploration inside a running kernel. Decisions compound, so every policy is judged by
replaying complete streams, never by per-reference accuracy; on-policy data (DAgger)
was tried and did not help (\S\ref{sec:eval-ablate}). Why linear: five heavier models,
trained the same way and also run in the kernel, were level with it at 20--150$\times$ the
cost (\S\ref{sec:eval-ablate}). The global model is trained on six workloads (B-tree,
graph, key-value, LZW, matmul, sort) and used unchanged on all others.}

\centering

reference string with R/W marks $\rightarrow$ LRU replay $\rightarrow$

\subsection{Training on Decisions, Not References}
\label{sec:design-train}
% Challenge C3 -> technique T3 -> ablations A3 (v1 vs v2; probation sweep; DAgger)

\finding{Observation.} A policy acts at an eviction, over the pages resident at that
moment, and a naive sample of those pages almost never contains the page just used
(\S\ref{sec:bg-naive}).

\finding{Solution.} \sys trains on recorded eviction decisions. Every training and
validation stream is replayed under LRU at 5, 10 and 20\% of its distinct pages; at a
sample of evictions we record up to 32 resident candidates with their features and
labels: always \belady's victim, always the four most recently accessed candidates
(recency-stratified recording), and the rest uniformly. This raises the share of
just-accessed rows from 0.6\% to 3.1\%. Second, a \emph{probation} rule: a page loaded
fewer than $p$ scans ago is not evicted while an older candidate exists, which is
\clock's second chance applied to a learned score. $p\in\{0,1,2,4\}$ is chosen per
scope on validation. Over the six training workloads this gives 5.22M training rows
from 377K decisions, and 0.91M validation rows from 43K decisions.

\subsection{Integer-Only Scoring}
\label{sec:design-int}
% Challenge C2 -> technique T2 -> ablations A2 (float vs 4/8/12-bit; linear vs MLP)

\finding{Observation.} xv6 saves no floating-point registers on a context switch, and a
production kernel avoids floating point on the fault path.
\verify{cite the Linux policy on kernel FPU use and its cost}

\finding{Solution.} The score of a candidate page is
\begin{equation}
s(\text{page}) = \sum_{j\in S} q_j\, X_j(\text{page}), \qquad
q_j = \operatorname{round}\!\left(\frac{w_j}{\sigma_j}\, 2^{b}\right),
\label{eq:score}
\end{equation}
where $X_j$ is feature $j$ in Q8 fixed point, $S$ is the selected subset (1--5
features), and the standardisation is folded into the weight. Means and the bias are the
same for every candidate and drop out of the arg-max. $\log(1+x)$ comes from a 256-entry
table plus a most-significant-bit search and a 1,024-entry mantissa table, within 1.04
Q8 units of exact. The same header computes features in the kernel and in the
simulator, so a model scores a page identically in both. The kernel's default weights
are the global model over five features (\feat{idle}, \feat{age}, \feat{dirty},
\feat{refaults}, \feat{rdist}; probation 4 scans).

\finding{Heavier models, in whole numbers too.} To test whether capacity pays, five
heavier models (a CNN over the aging bits, a deeper MLP, set-attention, boosted trees and
ranking trees) are converted to whole-number arithmetic with a shared evaluator that the
kernel and the simulator both compile, and selected per process like the linear weights.

\subsection{When the Model Is Wrong}
\label{sec:design-wrong}
% Challenge C4 -> technique T4 -> ablation A4 (deliberately wrong models). NON-NEGOTIABLE.
% Every accepted ML-for-OS paper has a design element here, not a sentence.

\plan{State the worst case first, then the layers that bound it.}
\begin{enumerate}
\item \textbf{Correctness never depends on the model.} The score only orders eligible
  candidates (the faulting process's own evictable frames). The kernel checks every
  returned victim against that set and falls back to \clock if it is not in it (counted
  as \texttt{policy\_fallbacks}). The same workload produces byte-identical output under
  every policy (data-invariance suite, \S\ref{sec:impl}). A bad model costs
  performance, not data. The fallback never fired in any correctness run (all eight
  policies and the five heavier models, with and without prefetch).

\item \textbf{Probation} keeps the newest pages out of the choice, removing the failure

\item \textbf{Validation-only selection.} Many feature sets are catastrophic: at 10\%
  memory, 113 of the 300 sets reach $3\times$ \clock or more on graph and 52 on kv.

\subsection{Bounding the Decision Cost}
\label{sec:design-cost}
% Challenge C5 -> technique T5 -> ablation A5 (sample size k vs faults and instructions).

\finding{Observation.} Scoring every eligible page costs about 340 instructions per
candidate, so the decision grows in a straight line with the resident set
(\S\ref{sec:eval-cost}).

\finding{Solution.} Score only $k$ randomly sampled candidates, drawn with a partial
Fisher--Yates shuffle over the candidate array (no extra memory). With $k=32$ the
decision costs about 11,700 instructions whatever the memory size, for 0 to 1 point of
faults; $k=16$ costs 5,850 instructions for 1 to 2 points. The weights are unchanged;
$k$ is a per-process setting.
% src: week-15 report, "In the xv6 kernel" (lzw 0.837->0.842, Twitter replays 0.876->0.875,
% patbench 0.853->0.861 at k=32); week_16 report section "What choosing a victim costs"

% -----------------------------------------------------------------------------
\begin{algorithm}[t]
\caption{\sys victim selection (\texttt{choose\_ml}), one eviction}
\label{alg:choose}
\begin{algorithmic}
\STATE {\bfseries Input:} eligible resident pages $C$, weights $q$, subset $S$, probation $p$, scan counter $t$
\STATE {\bfseries if} sample size $k$ is set {\bfseries then} $C \leftarrow k$ random pages of $C$ \hfill (partial Fisher--Yates)
\STATE $old \leftarrow$ false; \ $best \leftarrow \bot$
\FOR{each page $c \in C$}
  \STATE read and clear $A(c)$; update \feat{aging}, \feat{sfreq}, last-seen scan
  \STATE {\bfseries if} $t - \mathrm{load}(c) \ge p$ {\bfseries then} $old \leftarrow$ true
\ENDFOR
\STATE flush the TLB once if any A bit was cleared
\FOR{each page $c \in C$}
  \IF{$old$ {\bfseries and} $t - \mathrm{load}(c) < p$}
    \STATE skip $c$ \hfill (probation)
  \ENDIF
  \STATE $s_c \leftarrow \sum_{j\in S} q_j X_j(c)$ \hfill (integers, Q8)
  \STATE keep $c$ if $s_c > s_{best}$, or equal and loaded earlier
\ENDFOR
\STATE {\bfseries return} $best$ \hfill (kernel validates it; \clock if invalid)
\end{algorithmic}
\end{algorithm}

\section{Implementation}
\label{sec:impl}
% Budget: 0.5-0.75 page. Draft THIRD (Step 5.3). Self-check: a reviewer can estimate
% the overhead from this section alone; the simulator/real-kernel boundary is stated.
% DOUBLE-BLIND: no names, lab URLs, or repository paths that identify the authors.

\finding{A paging layer for xv6.} Stock \xv~\citep{xv6} allocates every page eagerly and
never evicts; it has no page-fault path for memory, no backing store and no
replacement policy. We added demand paging, a raw swap area outside the file system
(8,192 slots, 32\,MB), a frame table with per-process resident limits, FIFO, \clock,
Aging and a decayed LFU, synchronous and asynchronous prefetch, an event tracer, and a
control call (\texttt{vmctl}) that sets a process's limit, policy and weights: about
4,200 kernel lines over upstream xv6, all policies included. On the final build the same
workload produces byte-identical output under all eight policies and the five heavier
models, with and without prefetch.

\plan{Say why xv6: the whole fault path is visible and small, experiments are
deterministic and repeatable, and every decision can be traced. Say what is the same as
Linux (A/D bits sampled by scans; refault bookkeeping) and what differs (per-process

\finding{The learned policy in the kernel.} \texttt{choose\_ml} (60 lines, with a 14-line
sampler) scans the candidates as Aging already does and scores them with
Equation~\ref{eq:score}; a 63-line header computes the Q8 features, and a 203-line
evaluator runs the heavier models in whole numbers. Both headers are compiled into the
kernel and the simulator. The learned policy's bookkeeping adds 40 bytes to each
resident page's record (120 to 160 bytes: load scan, last-seen scan, sampled count,
refault count, refault distance) and 12 bytes to each swap slot (the eviction time and
refault count, the information Linux keeps in a workingset shadow entry). The linear
weights are an 80-byte record per process, set through \texttt{vmctl} with the model and
sample size, and inherited across \texttt{fork} and \texttt{exec}. The ten built-in
heavier models take 100,716 bytes of read-only kernel data; the kernel forms of ARC, LHD
and S3-FIFO share about 0.95\,MB of machine-wide state.

% sizes from GAWWY_HANDOFF_PAPER.md reply M5

\finding{Classical policies in the form a kernel can run.} ARC, LHD and S3-FIFO react to
every hit, which a kernel never sees. Each was adapted the same way: accessed bits are
read and cleared at every eviction, and a page found accessed counts as one hit since the
last look (the touch that loaded it is ignored); everything else follows the published
algorithm (ARC's four lists, ghost lists and adaptive target; S3-FIFO's small, main and
ghost queues; LHD's per-class hit and eviction histograms, with time in evictions). They
are 73, 34 and 44 lines in the kernel. Their simulator versions match independent
reference implementations on 570 traces, faults and evictions alike.
% src: week_16 report section "The three classical policies in the kernel"; kernel/vmpage.c choose_arck/s3fifo/lhd

\finding{Complete reference strings.} Each workload routes every access to its data
through one accessor that records \texttt{R} or \texttt{W} and the page number, hit or
miss, so the stream is a complete reference string, which \belady labels require. A
stream counts only if the run passes, the kernel reports the number of references and
bytes written, the extracted file matches both exactly, repeats are byte-identical, and
an independent model of the program, run on the host, produces the same string.
% src: ML_REPORT 2.2-2.3; week-16 report ("checked reference by reference against an independent model")

\finding{A validated simulator.} Feature selection needs tens of thousands of full
replays, so it runs in a C simulator. FIFO, LRU and \belady match an independent
implementation on all 534 stream--capacity cells; FIFO, \clock, Aging and LFU match a
naive re-implementation of the kernel logic in faults and write-backs; every \tierK and
\tierKp feature matches it on 11,792 evictions $\times$ 53 candidates; and the C scorer
reproduces each trained model's predictions. The kernel's benchmarks fill memory before
the traced part begins, so the simulator replays from filled memory too; started empty,
it misjudges some models (set-attention by up to 14$\times$).
% src: ML_REPORT 5.1; week-15 report "Why the kernel and the simulator disagree"

\finding{Measuring cost and running at scale.} Decision cost is counted in instructions
with QEMU in instruction-counting mode, which repeats to within 0.3\%; the timer-tick
counters of ordinary runs are too noisy for cost. The 2,375 kernel runs were split
between one desktop and cloud notebooks; 180 runs repeated on both gave identical faults,
evictions and writes. Training is cheap: the linear score is a closed-form fit, and on one
consumer GPU the MLP and CNN train in 48\,s and set-attention in 67\,s; the boosted and
ranking trees take 2--3\,s on a CPU.

\finding{Where it wins.} The learned score does best where recency is a poor guide:

\finding{The learned score has the highest overhead of any policy that pays.} Choosing a victim
costs 22,803 instructions with 68 candidates, about 340 per candidate: 55$\times$ \clock,
about twice ARC (11,934) and LHD (14,199) (Table~\ref{tab:cost}). The rest of an

and the Twitter replays (0.93). The CNN and MLP never pay: their break-even fault cost is

\subsection{Where the Learned Policy Does Not Help}
\label{sec:eval-loss}

The failures are specific and repeat across memory sizes.
\textbf{Tiny memory:} matrix multiply at 5\% (two frames) is 1.72 of \clock.
\textbf{Indirect access:} SpMV is 1.10 and 1.12 at 5\% and 10\%.
\textbf{One set of weights for every program:} graph is 1.01 and 1.60 at 5\% and 20\%,
though graph's own weights reach 0.60 at 10\%; choosing weights per program automatically
is open. \textbf{Nothing to learn:} on the Bloom filter every policy is 1.00.
\textbf{No write marks:} on the real Redis trace the score is 1.11 of \clock in simulation,
where the dirty bit carries no signal (LRU: 0.93). \textbf{Writes:} 4.75$\times$ \clock on
matmul and 4.22$\times$ on SpMV at 10\%. \textbf{Fast storage:} on flash the btree score
costs more time than it saves. The kernel runs have no guard; the simulator prototype cuts
the worst case from 1.86 to 1.36 (\S\ref{sec:design-wrong}).

\section{Related Work}
\label{sec:related}
% Budget: 0.7 page. Draft SEVENTH (Step 5.7). 2-4 categories that mirror the baseline
% groups; each ends with ONE sentence on how this paper differs. Cover OS/architecture
% venues, not just MLSys. Every baseline must appear here. Entries marked "verify" in
% references.bib must be checked before submission.
% =============================================================================

\finding{Page replacement heuristics.}
\plan{\belady's optimum~\citep{belady1966study}; the working-set
model~\citep{denning1968working}; stack distance~\citep{mattson1970evaluation};
\clock~\citep{corbato1968paging} and WSClock~\citep{carr1981wsclock};
LRU-K~\citep{oneil1993lruk}, 2Q~\citep{johnson1994twoq}, LIRS~\citep{jiang2002lirs},
ARC~\citep{megiddo2003arc}, CAR~\citep{bansal2004car},
CLOCK-Pro~\citep{jiang2005clockpro}; LHD~\citep{beckmann2018lhd}; recent simple
policies SIEVE~\citep{zhang2024sieve} and S3-FIFO~\citep{yang2023s3fifo}; in Linux,
MGLRU~\citep{linux_mglru}, refault distance~\citep{linux_workingset} and
DAMON~\citep{linux_damon}.}
\emph{Difference:} each fixes one rule for combining recency, frequency and
dirtiness, and most assume they see every hit; we run ARC, LHD and S3-FIFO in the form a
kernel can run and compare against them there. The learned score learns the combination
from the same kernel signals, and its features are the ones the Linux mechanisms already
maintain.

\finding{Learned cache replacement.}
\plan{CPU caches: Hawkeye~\citep{jain2016hawkeye} and Glider~\citep{shi2019glider} learn
from \belady's decisions; Parrot~\citep{liu2020parrot} imitates \belady with a neural
policy. CDNs: LRB~\citep{song2020lrb}. Storage caches: LeCaR~\citep{vietri2018lecar} and
CACHEUS~\citep{rodriguez2021cacheus} weigh LRU and LFU with online regret
minimisation.}
\emph{Difference:} these observe every access and are judged per request; \sys sees only
sampled accessed/dirty bits and refaults, computes in integers on the eviction path, and
is evaluated inside a kernel. \sys shares Parrot's imitation-of-\belady formulation, and
our oracle tier plays the role of its full-information features.
\plan{Add in-kernel work (related-work-notes.md): LearnedCache~\citep{qi2026learnedcache}
on cache\_ext~\citep{zussman2025cacheext}; PageFlex~\citep{yelam2025pageflex}; learned
heuristic tuning~\citep{xia2026lah}; paging with predictions and robust
fallback~\citep{lykouris2021jacm,wei2020,chledowski2021robust}.}

\finding{Learned operating-system components.}
\plan{In-kernel models: LinnOS~\citep{hao2020linnos} (I/O latency, a small NN in the
block layer); learned allocation~\citep{maas2020llama}; learned memory-access
prediction~\citep{hashemi2018learning}; the learned-OS vision~\citep{zhang2019learned}.
At MLSys, learned policies sit above the kernel: VM
allocation~\citep{barbalho2023vmalloc,ling2025lava}, vCPU
oversubscription~\citep{wang2025protorail}, storage placement~\citep{yang2025byom} and
NUMA placement~\citep{zhao2026catur}, and work on making them safe or
adaptive~\citep{mallick2022matchmaker,tan2023ouroboros,qiu2024flash,gohil2026uncertain}.}
\emph{Difference:} \sys puts a learned policy in the kernel's paging path, where the
budget is microseconds, the inputs are hardware bits, and the model must be integer-only.

\section{Discussion and Limitations}
\label{sec:discussion}
% Budget: 0.5 page. Draft EIGHTH (Step 5.8). FAQ form works well (uncertainty paper).
% At least three honest limitations, each with a mitigation or future-work line.
% The limitations below are the ones the collaborator's handoff says the text must state.
% =============================================================================

\finding{Does this transfer to Linux?} We have not shown it. Linux has the same limit for
anonymous memory: the MMU sets accessed and dirty bits and the kernel samples them. It
already keeps richer versions of the features the learned score uses: \feat{idle}
corresponds to a folio's MGLRU generation age, \feat{sfreq} to MGLRU tiers and DAMON's
access counts, \feat{dirty} to \texttt{PG\_dirty}, and \feat{refaults}/\feat{rdist} to
workingset shadow entries. A learned score could rank the folios of an MGLRU eviction
batch with the same whole-number dot product. The only Linux evidence so far is
indirect: Redis and SQLite traces recorded on Linux with
Valgrind~\citep{nethercote2007valgrind}, replayed in the simulator (\S\ref{sec:eval-info}).

\finding{Why a teaching kernel?} \plan{The whole fault path is small and visible, runs
repeat exactly, and every decision can be traced and replayed, which is what made the
kernel-to-simulator comparison possible. What differs from Linux: per-process (local)
replacement rather than global or cgroup reclaim; one benchmark process at a time on one
hart, so no lock contention on the eviction path; no page cache competing for memory;
timing in QEMU.}

\finding{Limitations.}
\begin{itemize}
\item \textbf{The fault cost is assumed.} Instruction counts are measured; the time a real
  page-in and write-back take is not, so the break-even results rest on assumed fault
  costs (8\,ms disk, 100\,\textmu s flash) and one instruction per nanosecond.
\item \textbf{Fourteen workloads, some close variants; six for training.} 5\% and 20\%
  memory use one stream per variant (51 streams), and the heavier models ran on ten; most
  differences between the best policies are inside the intervals.
\item \textbf{Adapted classical policies.} ARC, LHD and S3-FIFO ran in the form a kernel
  can run (accessed bits read at evictions), not as published. A per-hit form is
  impossible in a kernel that does not see hits; S3-FIFO's result in particular should not
  be read as the algorithm's.
\item \textbf{Faults, not writes.} The label is \belady's fault-optimal choice; the learned
  score does not reduce page writes on average, and writes 4--5$\times$ \clock on matmul
  and SpMV. A label that counts write-backs is future work.
\item \textbf{No guard in the kernel.} The learned score can be worse than \clock; the
  fallback guard exists only as a simulator prototype.
\item \textbf{Traced data only.} Reference strings cover each workload's data, not its code
  and stack pages (3--9 always-hot frames).
\end{itemize}

\label{sec:conclusion}
