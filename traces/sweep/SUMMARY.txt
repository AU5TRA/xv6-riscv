HOW TO READ THIS
------------------------------------------------------------------------------
FRAMES    the number of physical pages the kernel allowed the program.
          This is the real capacity the run executed under, read back
          from the kernel, not the number requested on the command
          line. Use this column, not the percentage in the filename.
COVERAGE  FRAMES as a percentage of the working set, i.e. how much of
          the program's memory actually fitted at once.
FAULTS    times the program touched a page that was not resident and
          the kernel had to fetch it from swap.
EVICTIONS times a resident page had to be thrown out to make room.

Within a workload the reference string is identical at every capacity --
the program does the same work regardless of how much memory it is
given. Only the fault and eviction counts change. That is what makes
the set usable: one reference string, six operating points.


SIZE HEADROOM
------------------------------------------------------------------------------
xv6 caps any single file at 67,382,272 bytes. A trace that reached the cap
would stop growing without raising an error, so the margin matters:

    WORKLOAD              BYTES     OF CAP         HEADROOM
    kvbench             944,948      1.40%       66,437,324
    btreebench        1,323,146      1.96%       66,059,126
    sortbench         9,276,354     13.77%       58,105,918
    graphbench       16,786,360     24.91%       50,595,912
    lzwbench         67,381,296    100.00%              976
    matmulbench       8,893,440     13.20%       58,488,832
    matmulbench       9,999,360     14.84%       57,382,912

All 36 traces were verified complete. lzwbench is the only one close to
the cap, with 976 bytes to spare; it was checked two independent ways.
Re-running any of these 36 configurations is safe, because the workloads
are deterministic and produce the same size every time. Increasing any
workload's size argument is not safe until a length check is added.
