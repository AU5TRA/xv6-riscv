==============================================================================
COLLECTED TRACE DATASET -- SUMMARY
==============================================================================

36 runs: six workloads, each at six memory capacities.
Each run records the reference string of the workload's own data (every
traced arena page it touched, in order) plus the kernel's own fault and
eviction counters at that capacity. The program's code and stack are not
traced, but they share the frame limit; see UNTRACED below.

Location:  traces/sweep/
  <run>.trace    the reference string, one 'T <page>' line per access
  <run>.log      the full run transcript and RESULT counters
  <run>.harness  the test-harness output for that run

Totals:    36 traces, 0.6 GB, 114,765,048 reference records

HOW TO READ THIS
------------------------------------------------------------------------------
LIMIT     the number of physical pages the kernel allowed the whole
          process -- traced data AND its own code and stack. Read back
          from the kernel, not the number requested on the command
          line. Use this column, not the percentage in the filename.
UNTRACED  estimated frames held by untraced code/stack pages. Measured,
          not assumed: the number of always-in-use extra pages for which
          FIFO over this trace reproduces the kernel's EVICTIONS. FIFO
          evicts the program's own text like any other page, and it
          faults straight back in, so these pages hold frames
          throughout the run.
ARENA     LIMIT - UNTRACED: frames actually available to the traced
          pages. This is the capacity to simulate the trace at.
COVERAGE  ARENA as a percentage of the traced working set.
FIT       how far that FIFO replay lands from the kernel's EVICTIONS.
          Beyond +/-5% ARENA and COVERAGE are shown as '?': those runs
          sit on an eviction cliff, where one frame changes evictions
          several-fold, so no single UNTRACED value is meaningful.
FAULTS    times the process touched a page that was not resident and
          the kernel had to fetch it from swap (code and stack included).
EVICTIONS times a resident page had to be thrown out to make room.

Within a workload the reference string is identical at every capacity --
the program does the same work regardless of how much memory it is
given. Only the fault and eviction counts change. That is what makes
the set usable: one reference string, six operating points.


SIZE HEADROOM
------------------------------------------------------------------------------
xv6 caps any single file at 67,382,272 bytes. A trace that reached the cap
would stop growing without raising an error, so the margin matters:

    WORKLOAD              BYTES     OF CAP         HEADROOM
    kvbench             944,948      1.40%       66,437,324
    btreebench        1,323,146      1.96%       66,059,126
    sortbench         9,276,354     13.77%       58,105,918
    graphbench       16,786,360     24.91%       50,595,912
    lzwbench         67,381,296    100.00%              976
    matmulbench       8,893,440     13.20%       58,488,832
    matmulbench       9,999,360     14.84%       57,382,912

All 36 traces were verified complete. lzwbench is the only one close to
the cap, with 976 bytes to spare; it was checked two independent ways.
Re-running any of these 36 configurations is safe, because the workloads
are deterministic and produce the same size every time. Increasing any
workload's size argument is not safe until a length check is added.
